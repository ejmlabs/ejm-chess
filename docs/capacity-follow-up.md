# Capacity measurements after the short run

These are bounded preparation scopes for OpenSpec task 18.6. None is armed,
approved for provider work, implemented as a runnable harness, or measured.
They preserve the original arena acceptance targets. The approved
[short capacity plan](capacity-qualification.md) and its consumed allowance
cannot authorize or fund another run automatically.

The owner approved the short first-tier run as the initial arena release gate
on 2026-10-21, alongside separate ranked, player-flow and operational gates.
The full-hour retention, real-calendar, six-region external WAN and later-tier
measurements below follow that release. They remain unrun and must not appear
as passing capacity or latency claims. Optional server analysis stays disabled.

## Common admission gate

The product owns each fixture, driver, native adapter and report. Use the
public Game, Competition, account, receipt, replay and cache contracts. Keep
shared UI, studio and harness packages outside these measurements. Production
limits, routes and data stay separate.

Each proposed run needs its own reviewed planning update, exact sealed source,
fresh isolated resources, permanent run identity, fixed UTC start and stop,
local native qualification and complete cost ledger before owner approval.
No proposed larger ceiling below changes the current implementation. Do not
reuse or renew the once-only 20,000-admission run, replace failed fixtures,
refund uncertainty, recycle IDs, backdate clocks or seed terminal results.

The ledger must include current subscriptions, prior and pending account usage,
whole billing units, setup, image storage where used, driver/region runners,
cleanup and retained evidence. Assume no shared included allowance. The
[dated price model](cost-estimate.md) is an estimate, not a fresh tariff check.
Unpriced services, missing metrics or inadequate headroom must remain visible
in the review. The October 22 policy uses one $100 monthly spending target,
usage alerts and an emergency stop (thresholds are kept in the private provider record). Earlier service allocations
and mandatory recovery reserves no longer apply. Each future run still needs
an explicit finite spending ceiling within available monthly headroom. The
first-tier run keeps its approved $25 incremental ceiling. These proposals
grant no additional work and are not required for initial release.
Use the [common-cycle ledger](cost-estimate.md#current-proof-financial-policy)
for started billing units counted once; differing cycles or quantities need a
rebuilt ledger and savings grant no work. A workload stop is not a hard provider
invoice cap.

Every manifest must bind these fields before it can be approved:

- Source, lockfile, bundle, config, corpus and driver digests.
- Account, Worker, D1 and namespace IDs; dedicated secret references, no values.
- Absolute setup, admission, dispatch, drain and final verification deadlines.
- Permanent admission, request, CPU, row, physical-storage and duration ceilings.
- Conservative operation reservations, controller overhead and in-flight margin.
- Named real regional egress paths and their costs, or explicit unrun regions.
- Stop commands, independent provider readback and unresolved-debt accounting.
- Disposal review within 30 days for raw synthetic data and sanitized reporting.

Stop admission permanently at the first limit or missing control read. Preserve
accepted IDs and unresolved work. At the fixed dispatch deadline stop generated
work; account for pending native calls through the final deadline. Failure to
prove shutdown fails the run and retains its permits and cost exposure.

## R: Full one-hour retention and retirement

Purpose: qualify the 72,000-hot-payload floor, retirement at 25 successes per
second, held evidence, retry progress and permanent history at the first tier.

| Proposed finite boundary | Maximum or required target |
| --- | --- |
| Proposed run spending ceiling | kept in the private provider record, within available monthly headroom |
| Total interval | 150 elapsed minutes |
| Synthetic accounts / events | 6,000 / three 2,000-entry rapid arenas |
| Permanently charged game IDs | 96,000 |
| Combined unfinished games | 1,000 |
| Simultaneously nonhibernatable objects, all classes | 1,536 |
| Generated Worker requests / CPU | 5,000,000 / 250,000,000 ms |
| Native DO request equivalents | 5,000,000 |
| DO SQLite writes / reads | 12,000,000 / 500,000,000 |
| D1 writes / reads | 2,000,000 / 100,000,000 |
| Physical DO / D1 storage | 3 GiB / 512 MiB |
| Synthetic evidence holds / injected retry cases | 1,000 / 100 |

Use native legal games and original timestamps. Sustain 20 finishes per second
for 75 minutes: 72,000 in the first hour and 18,000 in the next 15 minutes.
The remaining 6,000 IDs cover initial occupancy, fixed faults and uncertainty;
they are not replacement credit for missed stream targets. Keep unfinished
games within 1,000 while producing the stream. Reaching 72,000 retained payloads
does not allow admission to consume space reserved for accepted results.

No payload becomes eligible before its real terminal age reaches one hour.
At 20 new eligible records per second, steady traffic alone cannot demonstrate
25 successful retirements per second. Complete a fixed initial 400-game burst
within the 6,000 safety IDs, paced by the normal start allowance. Keep those
records outside the hold/fault set and preserve their original terminal times.
Accumulate at least 300 already-due unheld records plus the declared retry
margin before starting the measured interval. Then
measure at least 25 successful retirements per second for a continuous
60-second interval, alongside the continuing 20-result stream. Report warmup,
backlog growth and post-burst rates separately. The existing 32-attempt limit,
four archive calls in flight, matching version/digest and normal hold checks
stay in force. Do not lower an age or raise a limit to pass.

Apply the normal evidence-hold path to fixed synthetic records. Keep some held
past ordinary eligibility and release others through their supported path.
Inject at most the declared 100 retry cases, including lost acknowledgements
and unavailable projections. Show that due unheld records progress, a restart
preserves cursors and allowance, and no active or held payload is retired.
If a supported finite hold-release path is absent, record that case unrun.

Close new admission by minute 80. Continue only the fixed accepted-work and
retirement protocol until minute 140; allow ten final minutes for pending
native work and readback. Reconcile every admitted ID, terminal receipt, D1
archive marker, Game tombstone, score, PGN and remaining hold. Include actual
SQLite page use, not just logical row deletion. Missing retirement throughput,
driver schedules or shutdown evidence fails the relevant target.

The maximum duration envelope is 1,769,472 GB-seconds using the dated 0.128 GB
allocation model. It spans two excess duration units, before all other costs.
Local calibration must prove that the remaining dimensions and uncertainty fit
available headroom within the proposed run ceiling. These ceilings deliberately permit a failed qualification rather than an
automatic budget increase.

The 3 GiB storage ceiling is a known feasibility blocker, not evidence that
72,000 objects fit. The current Game and abuse schema creates eight table
roots, four text/composite-primary-key index roots and one schema page per
object. At an assumed 4 KiB page size, that is at least 52 KiB per Game and
3.5703 GiB for 72,000 before payloads, live objects and controllers. Native page
size and physical allocation still need measurement. If that floor holds,
this scope cannot arm as written. Prepare a reviewed storage/cost revision;
do not silently raise the 3 GiB cap or reduce the 72,000 target. Qualify trusted
incarnation shutdown and permit release before attempting 96,000 distinct IDs.

## C: Real hourly, daily and weekly cadence

Purpose: observe native cron/alarm scheduling and recovery across real calendar
boundaries. Fake clocks and compressed cadences cannot establish this result.

Propose one nine-day window, starting Saturday at 12:00 UTC and ending the
second following Monday at 12:00 UTC. The exact dates must be fixed before
approval. It includes two Sunday 16:00 weekly starts, daily 18:00 starts, hourly
blitz starts and time for accepted rapid games to drain under their normal
120-minute pairing and 40-minute game wall limits.

| Proposed finite boundary | Maximum |
| --- | ---: |
| Proposed run spending ceiling | $20, within available monthly headroom |
| Synthetic accounts / permanent game IDs | 120 / 96 |
| Combined unfinished games / nonhibernatable objects | 3 / 8, all classes |
| Generated Worker requests / CPU | 100,000 / 5,000,000 ms |
| Native DO request equivalents | 100,000 |
| DO SQLite writes / reads | 500,000 / 10,000,000 |
| D1 writes / reads | 100,000 / 10,000,000 |
| Physical DO / D1 storage | 1 GiB / 100 MiB |

Use fixed small entrant cohorts at named hourly, daily and both weekly events.
Allow other scheduled events to cancel truthfully when underfilled. Verify
published IDs and next-event times, registration closure, eligibility changes,
no-shows, pause/resume, repeat opponents, score ties, draining and finalization.
One fixture must remain unresolved until its original wall deadline, with no
fabricated winner or shortened wait.

The finite fault list contains one lost result acknowledgement, one real
Competition restart and one declared scheduler outage spanning an hourly
boundary. Recovery must create only the supported current/next work, preserve
accepted intents and points, and avoid catch-up floods. Read the ordinary event
retention and archived final standings after the nine days. Do not use a
busy-loop monitor or keep objects alive to observe them. Final readback must
show disabled private ingress and no future synthetic scheduling.

Eight continuously billed objects over nine days would use 796,262.4 GB-seconds
under the dated model, one excess duration unit. Other costs and uncertainty
must fit the $20 proposed slice. This measures calendar behavior at small load;
it does not replace the full retention or regional load measurements.

ranked reservations, four concurrent ranked games, two native attempt credits

The proposed incremental run ceiling is $25 within available headroom under
the single $100 monthly target. Earlier service allocations and mandatory

## L: Later 10,000-entry and 5,000-live tier

Purpose: qualify the original later tier only after the first-tier throughput,
retention, recovery, region and cost gates pass. The current entrant and game
maximums reject this workload. A reviewed architecture/limit change and proof
of shared reservations are prerequisites, not implicit outcomes of this plan.

Propose one separate 45-minute native window, 10,000 existing credential-backed
accounts, one 10,000-entry arena, at most 5,000 combined unfinished games and
12,000 permanent game IDs. Reserve ten minutes for setup, fifteen for full
occupancy and live moves, five for the fixed reconnect/recovery cases and
fifteen for shutdown and verification. Stop admission at minute 30 and all new
dispatch at minute 35. Keep raw work and expiry controls independent of the
driver. No production cap changes are authorized.

The proposed run spending ceiling is kept in the private provider record and sits within available monthly headroom.
Initial calibration ceilings are 6,144 simultaneous nonhibernatable
objects, 1,200,000 Worker requests, 60,000,000 Worker CPU ms, 1,000,000 DO request
equivalents, 5,000,000 DO writes, 500,000,000 DO reads, 1,000,000 D1 writes,
100,000,000 D1 reads, 3 GiB DO storage and 512 MiB D1 storage. At the dated
allocation model the duration ceiling alone is 2,123,366.4 GB-seconds, three
excess units. Prove all dimensions fit the ledger before approval; the limits
may expose that this scope cannot fit the budget. Failure requires a reviewed
new plan, not silently raising spending or shrinking the target.

Exercise 10,000 participant sockets and one 10,000-connection replacement burst,
real legal moves under occupancy, simultaneous native results, conflicting and
matching duplicates, fixed outbox and D1 faults, and normal reservation release.
Use the original acknowledgement/projection targets and report offered,
accepted and acknowledged rates. Repeat the original named regional paths
and real cached standings workload. Never infer a WAN path from a colo hint.
Choose any higher supported recovery rate before sealing; do not describe the
first tier's 1,000-result recovery as 5,000-game recovery.

This short later-tier window still does not prove its own full-hour retention,
long-term ledger growth or monthly operating cost. Derive and separately bound
those measurements from passing first-tier evidence before selecting a public
later-tier limit.
